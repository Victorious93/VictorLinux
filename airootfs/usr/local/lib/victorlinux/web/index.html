Folders to read

Only folders you add here are read. System folders and VictorLinux secrets are refused; hidden folders and symlinks are skipped. Removing a folder deletes it from the index, never from disk.

Meaning search (optional)

Keyword search always works. For search by meaning, pick an embedding GGUF from your model folders; VictorLinux runs it with llama-server on 127.0.0.1 only. Without one, the chat model is used if it serves embeddings.

Where your files go

Use the drives you already own: boot from the USB stick, keep models on a big external drive, documents on the internal SSD. Drives keep their contents, label and format; choosing one only creates the folder you name. Active destinations and whether they are persistent are listed here and by victor-storage status.

Choose a destination

Drives on this PC

Internal disks, external drives, USB sticks and SD cards. App state (settings, chats, API-key hash) needs a Linux filesystem (ext4/btrfs/xfs); exFAT, NTFS and FAT32 drives are fine for models, documents, downloads and backups. FAT32 cannot hold any single file of 4 GiB or more. A drive labelled VICTORDATA (legacy TORIDATA) is found automatically; nothing else needs a special label. The operating system itself does not persist.

Storage health

Free space where VictorLinux saves, and read-only SMART health of the disks behind it. Nothing is written to any disk.

Encrypted backups

Backs up settings, chats, document-search settings and PC reports, encrypted with a passphrase only you know. Models are not included (re-import them). API keys and TLS keys are left out unless you tick the box. There is no recovery without the passphrase.

Restore

Step 1: pick a backup and check it (decrypted in memory, every file verified). Step 2: restore. Files that would be replaced are copied to a pre-restore folder first.

PC inference server (for DroidCommand-AI and other clients)


  
Remote inference never allows tool execution on this PC. Binding to a LAN/VPN address is your explicit choice; prefer a private VPN (see docs/remote-access.md).

 
API keys
One key per app or device. A key is shown once, stored only as a hash, and stops working the moment you revoke it or it expires. The per-key limit caps requests per minute. The usage log keeps the time, key name, path and status, never the key or the request content.

  

   

   

   

  

  

  
Recent requests

 
Pair phone (off until you press it)
Shows a QR code for 10 minutes. It contains this PC's gateway address, its TLS certificate fingerprint and a single-use pairing token, never an API key. The phone trades the token for its own named key over TLS, and the key is shown only to the phone. Three wrong tokens close the window. There is no LAN discovery: the phone uses the address in the QR.

  

  

  


 
Pair phone (Bluetooth)

  
Lets the Victorious Keyboard app act as a standard Bluetooth keyboard and mouse. Bluetooth stays off by default. This makes the PC discoverable for 120 seconds, shows the passkey, and trusts the phone only after you confirm. It does not enable Bluetooth on boot.

  
Off by default.

  

  

  

 
Wi-Fi keyboard (off until you turn it on)

  
An optional WebSocket input service for Victorious Keyboard on the LAN. Auth uses the same victorpc://pair QR flow (v1) and a per-device Bearer token, never stored in the QR. The service is off by default, the admin toggle is localhost-only, and unauthenticated or replayed messages are rejected. See docs/VICTOR_INPUT_PROTOCOL.md.

  
Off by default.

  

  

   

   

  

   

  

  

 
USB keyboard and mouse

  
Victorious Keyboard can also act as a USB keyboard and mouse over a data cable (root and ConfigFS on the phone). That needs no PC software. This has not been tried on a real VictorLinux boot, so treat it as Likely. Details: docs/phone-as-keyboard.md.

Phone fleet
Coordinator for up to 4 DroidCommand phones. Off until you start it; local-only until fleet networking is enabled (victor-fleet config --enable-network ADDR). Phones keep their own approvals; Revoke takes effect immediately.

Draft for the phone's owner to review
This hands a draft to VictorSMS on the selected phone. The phone shows the recipients, the sending identity it will use and the contents; only the owner's Send button there submits it. Declining sends nothing. Mail passwords never leave the phone, and message bodies are not written to the fleet logs.
